# 인증과 상태 관리

## 1. 비밀 값 두 가지

| 값            | 누가 발급·설정하는가 | 어디에서 사용하는가                  |
| ------------- | -------------------- | ------------------------------------ |
| 서비스 API 키 | 백엔드 설정          | Next.js → FastAPI의 Bearer 인증      |
| 수사 토큰     | FastAPI의 수사 생성  | 특정 수사에 접근할 때 `X-Game-Token` |

서비스 API 키는 `.env.local`의 서버 설정으로 읽습니다. 수사 토큰은 생성 응답에서 받아 HttpOnly 쿠키에 넣습니다. 둘은 같은 값이 아니며 목적도 다릅니다.

게임 ID만 안다고 그 수사의 데이터에 접근할 수 있는 구조가 아닙니다. FastAPI가 수사 토큰도 확인합니다.

## 2. 수사 쿠키

현재 쿠키 이름은 `cd_game_id`, `cd_game_token`입니다.

| 속성     | 현재 값 또는 조건               | 의미                                 |
| -------- | ------------------------------- | ------------------------------------ |
| HttpOnly | true                            | 브라우저 JavaScript의 직접 읽기 차단 |
| SameSite | Lax                             | 다른 사이트 요청에서 쿠키 전송 제한  |
| Secure   | 요청 프로토콜이 HTTPS일 때 true | HTTPS 환경에서 보호                  |
| Path     | `/`                             | 사이트 전체 경로에 적용              |
| Max-Age  | 604800초                        | 발급 시점부터 7일                    |

수사를 생성할 때 설정하며 모든 조회마다 자동으로 7일을 연장하는 코드는 아닙니다. 브라우저 개발자 도구에서는 쿠키를 확인할 수 있으므로 사용자 자신에게도 절대 보이지 않는 값이라는 뜻은 아닙니다.

쿠키 삭제·만료 후에는 현재 UI만으로 예전 수사를 골라 복원할 수 없습니다. DB 기록과 브라우저의 접근 수단이 별개이기 때문입니다.

## 3. 상태 복원

쿠키가 없을 때 `GET state`는 오류 대신 `{state:null}`을 반환합니다. 첫 수사를 시작할 수 있는 정상 초기 상태입니다.

쿠키가 있지만 FastAPI 상태 조회가 404이면 BFF는 두 쿠키를 삭제하고 `{state:null, sessionExpired:true}`를 돌려줍니다. DB를 교체했거나 토큰에 맞는 기록이 사라진 경우에 해당할 수 있습니다. 모든 404를 이 방식으로 처리하는 것이 아니라 **state 조회의 404**에 적용합니다.

서비스 키가 틀린 401이나 서버 연결 실패까지 초기 상태로 조용히 바꾸지는 않습니다. 오류로 확인해야 합니다.

## 4. 공식 상태와 UI 초안

공식 상태는 FastAPI의 `state`입니다. `phase`, `examined`, `statements`, `findingDetails`, `derivedEvidence`, `notes`, `questions`, `verdict` 등이 들어 있습니다.

UI는 현재 메뉴·인물·입력 질문·첨부 선택·검색어·모바일 메뉴·팝업을 따로 보관합니다. 체크박스를 선택하는 것만으로 추론이 생성되지 않고, 메모를 입력하는 것만으로 DB 저장이 완료되는 것도 아닙니다.

브라우저 localStorage에는 오프닝 표시 여부만 저장합니다. 공식 수사 데이터를 localStorage에 저장하는 구조는 아닙니다.

## 5. revision은 저장 버전

현재 상태가 revision 4라면 다음 변경 요청은 `expected_revision: 4`를 보냅니다. FastAPI가 확인한 실제 버전이 다르면 409가 발생할 수 있습니다.

예를 들어 두 탭이 모두 버전 4를 보고 있는데 A 탭이 먼저 메모를 저장하면, B 탭의 오래된 버전 요청은 거절될 수 있습니다. BFF나 화면이 무조건 값을 덮어쓰지 않도록 하기 위한 계약입니다.

`game-client.ts`의 `accept`는 같은 게임의 낮은 revision 응답으로 최신 메모리 상태를 되돌리지 않습니다. 실제 상태 변화가 없는 반복 행동은 버전이 꼭 증가하는 것은 아닙니다.

## 6. UUID는 한 행동의 번호

`crypto.randomUUID()`로 행동마다 요청 ID를 만듭니다. 서버가 요청을 처리했지만 응답이 끊겼다면 성공 여부를 바로 알 수 없습니다. 이때 새 UUID로 같은 행동을 보내면 중복 처리 가능성이 생깁니다.

따라서 전송 예외와 `BACKEND_UNREACHABLE`, `BACKEND_TIMEOUT`, `INVALID_RESPONSE`, `operation_in_progress`만 결과가 불확실한 요청으로 분류해 `pending`에 보관합니다. FastAPI가 생성·검증 실패로 확정해 반환한 502·504는 보류하지 않습니다. HTTP 상태만 보고 모든 5xx를 재전송하면 새 질문까지 이전 실패에 막힐 수 있습니다. 다음 변경 요청을 처리할 때 이전 요청을 **같은 본문·같은 UUID로 먼저 확인**합니다.

다음 입력의 행동과 내용까지 같으면 복구된 응답을 반환합니다. 입력이 다르면 이전 요청 결과를 확인한 뒤 새 행동을 이어갑니다. 재시도마다 무조건 새 질문으로 소비하는 방식이 아닙니다.

입력 오류처럼 확정 거절된 요청은 보류하지 않습니다. 일반 409에서는 최신 state를 조회하고 오류를 전달하며, 사용자 행동을 다른 revision에 자동으로 재적용하지 않습니다.

보류 요청은 브라우저 탭 메모리에만 있습니다. 새로고침 이후까지 UUID 재시도 기록을 영구 보관하는 기능은 없습니다. 새로고침하면 서버의 현재 상태를 다시 읽습니다.

## 7. 메모와 심문을 같은 큐에 넣는 이유

자동 저장과 질문 전송이 동시에 같은 revision을 사용하면 서로 충돌할 수 있습니다. `requestGame`은 Promise 큐로 행동을 직렬화합니다.

```text
메모 저장 요청
  → 최신 state 반영
    → 그 버전으로 심문 요청
      → 최신 state 반영
```

`useCaseGame`의 `actionLock`과 `busy`는 일반 행동의 중복 클릭을 줄입니다. 자동 저장도 같은 `requestGame` 큐를 사용합니다. 처리 중 타이핑한 최신 메모를 이전 저장 응답으로 덮어쓰지 않도록 저장 스냅샷과 최신 입력을 비교합니다.

이 큐는 현재 탭의 요청 순서를 정리합니다. 여러 탭·다른 사용자까지 하나의 브라우저 큐로 묶는 기능은 아닙니다. 최종 동시성 제어는 백엔드의 revision·예약·확정 경로가 담당합니다.

## 8. 출처 검사와 중계 제한

변경 요청은 Origin이 있어야 하며 요청 Host·프로토콜로 구성한 출처와 일치해야 합니다. 다른 사이트나 Origin 없는 변경 요청은 403입니다. GET은 같은 방식의 Origin 검사를 하지 않습니다.

BFF는 허용된 경로만 FastAPI에 전달합니다. 브라우저가 임의 호스트·다른 게임 ID·임의 인증 헤더를 지정하는 입력은 지원하지 않습니다. JSON 변경 본문은 객체여야 하고 현재 크기 제한은 100,000바이트입니다.

클라이언트의 UI 제한을 우회하더라도 FastAPI의 자료 획득·토큰·규칙 검사를 통과해야 합니다.

## 9. 캐시와 남는 기록

API 호출은 `no-store`를 사용하며 수사 응답에도 캐시 금지 헤더를 설정합니다. 그렇다고 브라우저 메모리·SQLite·테스트 보고서까지 모두 사라진다는 뜻은 아닙니다.

수사 기록의 저장 위치는 백엔드 DB입니다. `.reports`에는 검사 때의 입력·출력·대화·종결 정답 설명이 포함될 수 있습니다. 공개하려면 필요한 내용을 먼저 확인하세요. 보고서에는 API 키나 쿠키 헤더를 기록하지 않도록 구현되어 있습니다.

## fallback은 보류 요청이 아니라 완료된 답변

기본 플레이는 생성 오류를 200 fallback으로 복구하고 서버가 대화를 확정합니다. 정상 응답으로 처리하므로 pending에 남기지 않습니다. 질문 1회가 소비되지만 같은 UUID는 재차 소비하지 않습니다. strict 서버가 확정된 생성 오류를 반환한 경우에도 새 질문을 이전 실패에 막히게 만들지 않습니다. 실제 통신 단절·중계 시간 초과는 여전히 결과가 불확실하므로 별도 복구합니다.
