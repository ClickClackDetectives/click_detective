# 원본 UI·UX 유지와 비교 검사

## 1. 검사 목적

`share_project`의 화면을 유지한다는 요구를 코드·화면·동작 세 층에서 확인합니다.

| 검사           | 확인하는 것                          | 확인하지 못하는 것        |
| -------------- | ------------------------------------ | ------------------------- |
| 바이트 비교    | 특정 원본 파일이 동일한지            | 모든 실행 상태의 화면     |
| 스크린샷 비교  | 지정 상태·해상도에서 화면이 동일한지 | 모든 브라우저·모든 데이터 |
| 브라우저 조작  | 실제 버튼·저장·복원이 연결되는지     | 실제 모델 대사의 품질     |
| HTTP 전체 진행 | 전체 게임 API가 연동되는지           | 모든 화면의 픽셀          |

## 2. 소스 동일성 검사

`tests/ui-source.test.ts`가 다음을 비교합니다.

- `app/globals.css`, `app/layout.tsx`, `app/styles`의 모든 원본 스타일 파일
- `case-app.tsx`, `app-header.tsx`, `navigation.ts`
- `case-opening.tsx`, `evidence-dialog.tsx`
- 홈·사건실·노트·타임라인·쟁점 화면

이는 지정한 파일이 바이트 단위로 같다는 뜻입니다. 서버 검색으로 바꾼 자료실·증언·추론 화면이나 연결 안내를 고친 파일까지 바이트 동일성을 요구하지는 않습니다. 그런 부분은 마크업을 유지하고 브라우저 결과를 비교합니다.

## 3. 실제 브라우저 비교 과정

`npm run test:ui`는 먼저 HTTP 전체 게임을 진행한 뒤 UI 검사를 호출합니다.

1. 임시 폴더에 원본 소스 사본을 만듭니다.
2. 원본 `node_modules`와 `public`을 참조해 비교 서버를 실행합니다.
3. 비교용 원본의 `/api/game/...` 요청은 브라우저에서 같은 수사 state로 응답하도록 모의 처리합니다.
4. 새 프로젝트는 실제 Next.js BFF와 fixture FastAPI를 사용합니다.
5. 같은 상태·해상도에서 두 페이지를 이동하고 스크린샷을 저장합니다.
6. PNG 버퍼가 완전히 같은지 비교해 `exactPixels`를 기록합니다.
7. 새 프로젝트에서는 실제 클릭·요청·자동 저장·복원을 검사합니다.

원본 저장 API를 실행해 원본 플레이 기록을 바꾸는 방식이 아닙니다. 픽셀 비교의 주요 수사 상태는 전체 게임을 마친 종결 상태이고, 그 뒤 동작 검사에서 새 수사를 진행합니다.

## 4. 비교 조건에서 맞추는 것

데스크톱 viewport는 1440×1000, 모바일은 390×844입니다. 스크린샷은 전체 페이지를 캡처하므로 이미지 높이가 viewport보다 길 수 있습니다.

두 브라우저 컨텍스트에서 외부 Google 폰트 요청을 차단하고 같은 로컬 폰트 환경을 사용합니다. reduced motion을 설정하고 스크린샷 애니메이션을 비활성화합니다. 원본 개발 서버의 Next.js 개발 표시도 숨깁니다. 이는 게임 UI가 아닌 비교 환경 차이를 줄이기 위한 처리입니다.

원본의 ‘AI 미연결’ 설명은 비교 페이지 DOM에서만 새 연결 안내와 맞춥니다. 소스 원본을 수정하는 것은 아닙니다. 해당 안내 변경이 제품상 허용한 차이라는 점을 결과 해석에 포함해야 합니다.

현재 환경에서는 `.browser-libs/fonts.conf`가 있으면 같은 폰트 설정을 사용합니다. 다른 PC에서 그대로 같은 PNG가 생성된다는 보증은 아니지만, 그 PC의 두 페이지는 같은 조건으로 비교합니다.

## 6. 실제 상호작용 5개 묶음

| 검사 묶음      | 확인한 동작                                     |
| -------------- | ----------------------------------------------- |
| 새 수사·오프닝 | 다시 수사 확인 → 새 수사 → 오프닝 표시·닫기     |
| 자료 열람·제시 | 와인 자료 열람 → 팝업 → 심문실 자료 선택        |
| 심문 API       | 강민호 선택 → 질문 → 실제 fixture API 답변 표시 |
| 자동 저장      | 입력 → 해당 PUT 성공 대기 → 서버 notes 값 확인  |
| 복원           | 새로고침 → 수사 진입 → 저장된 메모 확인         |

브라우저 페이지 오류도 수집해 빈 배열인지 확인합니다. 오프닝 표시·닫기와 Range 응답 검사가 영상의 모든 프레임·오디오 코덱·모든 자동 재생 정책을 검증한다는 뜻은 아닙니다.

## 7. 보고서 읽는 방법

```text
.reports/
  integration.json
  integration-server.log
  ui/
    comparison.json
    desktop-home-original.png
    desktop-home-actual.png
    ...
```

`comparison.json`의 `screens`에서 화면별 `exactPixels`, `checks`에서 완료한 동작 묶음, `consoleErrors`에서 페이지 오류, `passed`에서 최종 성공 여부를 확인합니다. 실패했다면 같은 접두사의 original/actual 이미지를 나란히 확인합니다.

예를 들어 노트 배경만 다르면 CSS 파일뿐 아니라 `/assets/notebook-paper.png`의 응답도 확인해야 합니다. 본문 내용이나 카운트가 다르면 두 페이지에 같은 state가 들어갔는지 확인합니다. 데이터 공급 차이를 숨기기 위해 무조건 CSS를 수정하지 않습니다.

## 8. 현재 보관된 확인 결과

보고서의 생성 시각은 2026-11-13 UTC 기준이며, 기존 실행에서 다음이 확인되었습니다.

- 화면 18개: 전부 `exactPixels: true`
- 브라우저 동작 묶음 5개 완료
- 브라우저 페이지 오류: 0개
- 실제 Next.js → fixture FastAPI HTTP: 149건 성공
- 전체 게임 진행률: 100%, 고발 점수: 100
- 별도 백엔드 pytest: 15개 통과
- 프런트엔드 단위 검사: 5개 통과, 타입 검사·프로덕션 빌드 통과

문서 재작성에서는 저장된 보고서와 현재 코드를 확인했습니다. 이 수치를 새로운 검사 실행 결과로 다시 기록한 것은 아닙니다. 보고서는 재실행으로 갱신되므로 생성 시각과 현재 실행 출력을 함께 확인하세요.

## 9. 동일성의 범위

원본 UI·UX를 유지하는 구현과, 특정 조건에서 이를 확인한 검사 결과를 함께 제공합니다. 테스트한 상태·해상도에서는 동일했지만 모든 브라우저·폰트·화면 크기·입력·네트워크 장애 조합의 수학적 동일성을 보증하는 것은 아닙니다.

실제 LLM 대사는 생성 결과에 따라 달라집니다. 같은 레이아웃과 동작을 유지하더라도 대사 길이 때문에 말풍선 높이는 달라질 수 있습니다. 실제 모델의 양자화·어댑터·품질은 [백엔드 모델 안내](../../click_detective/docs/05_LLM_양자화_멀티에이전트.md)를 기준으로 별도 확인합니다.
