# 08. 테스트·진단·문제 해결

[목차](README.md) · [기존 검사 결과](검사_결과.md)

## 1. 기본 검사

```bash
cd ~/reverse/click_detective
source .cd_venv/bin/activate
python -m pytest -q
```

검사 건수는 현재 실행 출력을 확인하세요. langsmith의 Python 사용 중단 예고 경고 13개가 관찰된 이력이 있습니다. tests는 명시적인 fixture 설정·임시 SQLite·프로젝트 내부 데이터를 사용합니다. 실제 .env의 local 모드로 모델을 자동 로딩하지 않습니다.

| 테스트 파일             | 검사                                                                              |
| ----------------------- | --------------------------------------------------------------------------------- |
| test_game.py            | 사건·자산·인증·수사 권한·중복·revision·자료·전체 게임·거절                        |
| test_runtime.py         | 실제 LangGraph 3노드, strict 모드의 모델 실패 무소비, 생성 중 충돌, 경로 커버리지 |
| test_live_llm_runner.py | 실서버 도구의 판정·마스킹·오류·시간 초과·NF4 진단 검사, 모의 모델 사용            |
| conftest.py             | 공통 클라이언트·게임 생성·입력/출력 기록·토큰 마스킹                              |

일부 함수는 매개변수화되어 한 함수가 여러 검사로 실행됩니다. 함수 개수와 pytest 결과 개수는 다를 수 있습니다.

## 2. 입력·출력 보고서

.reports/pytest.json에는 fixture 모드, passed/failed, tests별 name/outcome/exchanges가 저장됩니다. exchanges에는 메서드·경로·본문·마스킹한 헤더와 실제 상태·응답 본문이 있습니다. 이미지·영상은 형식·바이트 수로 요약합니다.

Authorization·X-Game-Token·game_token은 마스킹합니다. 질문·메모·응답은 포함될 수 있습니다. HTTP가 없는 규칙 검사도 결과 항목은 있지만 exchanges가 빈 배열일 수 있습니다. 같은 이름으로 다시 실행하면 보고서를 갱신합니다.

## 3. 실제 모델 검사와 차이

테스트 통과는 실제 모델 파일·호환 어댑터·GPU 양자화 실행·의미 정확도·VRAM을 입증하지 않습니다. 기본 테스트의 ApprovedModel은 엄격한 내부 형식을 재현하는 모의 모델입니다.

실제 검사는 local로 서버를 실행하고 /docs 또는 별도 HTTP 클라이언트로 수사를 시작해 심문합니다. 이전 share_backend의 test_backend_apis.py가 현재 프로젝트에 있는 것은 아닙니다. 현재 scripts/test_llm_api_live.py가 별도 실서버 심문 검사를 제공합니다.

## 4. 진단 JSONL

local 그래프의 .data/dialogue-traces.jsonl은 요청마다 한 JSON 줄을 기록합니다. request_id로 HTTP 응답과 연결합니다. pipeline_version·설정의 안전한 목록·단계 시간·시도 번호·입출력 토큰·메모리·거절 코드 등을 확인합니다.

model_input은 실제 입력 토큰과 상한, generation_format은 기대 형식·관찰 외형·문자 수입니다. 원문을 저장하지 않으므로 JSON 오류의 실제 문자열까지 복원할 수는 없습니다.

PyTorch allocated/reserved/peak는 해당 프로세스의 수치입니다. nvidia-smi의 전체 GPU 메모리에는 화면 출력·다른 프로그램도 포함됩니다. 시간 초과 후 아직 진행 중인 CUDA 작업의 최종 이벤트는 종료 시점 기록에 없을 수 있습니다.

## 5. 오류별 확인 순서

| 현상                                | 확인                                                                                           |
| ----------------------------------- | ---------------------------------------------------------------------------------------------- |
| 401                                 | CLICK_API_KEY와 Authorization Bearer 형식                                                      |
| 404 수사                            | 게임 ID·X-Game-Token 쌍                                                                        |
| 409 state_revision_conflict         | 최신 상태 조회 후 새 행동 UUID로 재요청                                                        |
| 409 operation_in_progress           | 같은 요청이 아직 실행 중인지 확인                                                              |
| 409 state_changed_during_generation | 다른 행동이 상태를 변경했는지 확인                                                             |
| 409 scenario_version_conflict       | 수사의 고정 버전과 현재 데이터 패키지                                                          |
| 422 입력                            | 필드 이름·UUID·자료형·추가 필드·질문 길이                                                      |
| 422 자료                            | 단계·실제 열람·진술 기록·추론 생성 조건                                                        |
| 429                                 | 질문 25회 한도                                                                                 |
| 502/504                             | strict 모드 여부·X-Generation-Error·진단 확인. 기본 플레이의 생성 오류는 200 fallback으로 복구 |

critical_* 또는 evidence_* 오류는 지원되는 규칙을 통과하지 못한 결과일 수 있습니다. 실제 내용이 틀렸는지, 모델이 근거를 잘못 골랐는지, 정상 표현을 사전이 읽지 못했는지 구분해야 합니다. 오류를 임의로 PASS로 치환하지 않습니다.

## 6. 저장·운영 메모

DB와 진단 파일은 자동 기간 정리·백업·회전 정책이 구현돼 있지 않습니다. 운영 전에 보존 정책을 정해야 합니다. 같은 모델을 다른 서버·노트북에서 동시에 로딩하면 별도 GPU 메모리를 사용합니다. 별도 프로세스에서 empty_cache를 호출한다고 실행 중인 서버의 모델이 해제되는 것은 아닙니다.

## LLM 심문 API만 실서버로 확인

전체 fixture 검사 대신 이미 켜진 local 모델 서버를 대상으로 하려면 [실서버 LLM 검사 안내](11_LLM_멀티에이전트_실서버_테스트.md)를 사용하세요. `scripts/test_llm_api_live.py`가 자기소개·동선·자료 제시 심문만 검사하며, 같은 서버의 JSONL을 지정하면 세 에이전트와 NF4 실행 진단도 확인합니다.

## 다른 질문도 같은 502가 반복될 때

이전 진단에서 같은 request_id가 반복되면 Next.js가 새 질문 대신 이전 요청을 복구 중인지 확인합니다. 확정된 생성·검증 실패 502는 보류 요청으로 남기지 않도록 수정했습니다. 실제 통신 단절·중계 시간 초과는 중복 확정을 막기 위해 같은 UUID를 유지합니다.

`complete-evidence-v6`부터 평문 재생성에 JSON을 요구하던 모순 안내를 수정하고 필수 문장·검증 index 개수를 명시합니다. 누락 검증·false에 근거 번호가 붙은 응답은 계속 거절합니다. 승인 정보가 없는 질문은 기존 중립 답변(fixed)으로 처리하며 새 비밀이나 사실을 만들지 않습니다.

업데이트 뒤 FastAPI와 Next.js를 다시 실행하고 브라우저를 새로고침하세요. 백엔드만 재시작해도 기존 탭 메모리에 남은 pending은 지워지지 않습니다. 실제 모델 생성·검증 실패가 남으면 새 request_id와 현재 semantic-paraphrase-v7 진단으로 확인해야 합니다.

## 기본 플레이의 실패 복구 검사

`test_reply_availability.py`는 502·504·내부 문맥 오류·런타임 오류·잘못된 출력이 발생해도 승인 원문 답변·대화·질문 1회가 확정되는지 검사합니다. 같은 UUID 재전송은 중복 차감하지 않습니다. 승인된 인정 대사의 쟁점 저장도 확인합니다.

공통 conftest는 오류를 직접 관찰하려고 fallback_on_error=false를 명시하고, 플레이 복구 테스트만 true로 바꿉니다. 기존 strict 실패 무소비 테스트와 모순되지 않습니다. [전체 정책](12_질문_응답과_복구_정책.md)
