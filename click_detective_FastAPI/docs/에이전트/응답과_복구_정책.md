# 질문 응답·복구·쟁점 저장 정책

## 1. 질문 응답과 쟁점은 별개입니다

수사 화면에서 전송한 유효한 질문에는 쟁점 발견 여부와 관계없이 답변을 준비합니다. 쟁점 조건을 충족하지 못했다는 이유만으로 대화를 중단하지 않습니다.

승인된 사실이 있으면 모델 생성·검증을 먼저 시도합니다. 그 과정이 실패하면 검증 실패한 모델 문장을 노출하지 않고 **서버가 승인한 원문만 조립한 대사**로 복구합니다. 승인 정보가 없는 질문은 중립 답변을 반환합니다.

## 2. 응답 유형

| 상황                                | finish_reason | 대사 출처                          | 처리                  |
| ----------------------------------- | ------------- | ---------------------------------- | --------------------- |
| 실제 모델 생성·검증 성공            | stop          | 검증된 모델 대사                   | HTTP 200 및 대화 확정 |
| 승인된 정보가 없음                  | fixed         | 중립 안내                          | HTTP 200 및 대화 확정 |
| 명시적인 fixture 모드               | fixed         | 승인 원문 또는 중립 안내           | HTTP 200 및 대화 확정 |
| 기본 플레이 모드에서 생성·검증 실패 | fallback      | 승인 원문, 사실이 없으면 중립 안내 | HTTP 200 및 대화 확정 |
| 별도 strict 모드에서 생성·검증 실패 | 응답 없음     | 오류를 그대로 관찰                 | 오류 반환, 확정 안 됨 |

기본값은 `CLICK_FALLBACK_ON_ERROR=true`입니다. false는 모델 실패 자체를 관찰할 별도 품질 검사 설정입니다. 같은 이름의 프로세스 환경변수가 파일 설정을 덮어쓸 수 있으므로 실제 서버를 재시작한 뒤 유효 설정을 확인합니다.

fixed·fallback은 실제 LLM 생성 성공인 stop과 다릅니다. 사용자에게 답을 제공했다고 모델 검증 성공으로 표시하지 않습니다.

## 3. 질문 횟수와 기록

stop·fixed·fallback이 정상 확정되면 모두 질문을 1회 소비하고 질문/답변 2개 메시지를 기록합니다. 같은 UUID와 본문의 재전송은 캐시 결과를 반환하므로 다시 차감하지 않습니다.

복구 답변도 실제로 사용자에게 제공한 대화이므로 기록합니다. ‘모델이 한 번 실패했으니 질문을 소비하지 않는다’는 설명은 기본 플레이 정책에 맞지 않습니다. **strict 모드에서 응답을 확정하지 못한 요청**과 구분해야 합니다.

## 4. 증언·쟁점의 처리

`Planner.prepare`가 먼저 공개 가능한 사실·공식 증언·새 쟁점 계획을 만듭니다. 모델은 새로운 쟁점을 임의로 만들지 않습니다.

- 쟁점 계획이 없으면 답변은 반환해도 새 쟁점은 추가하지 않습니다.
- 쟁점 조건이 충족되면 승인된 인정 대사를 생성하거나 원문으로 복구한 뒤 해당 쟁점을 확정합니다.
- 한 번에 자료 1개를 제시하며, 같은 인물에게 성공적으로 제시한 과거 자료와 이번 자료를 누적합니다.
- 열람했다는 사실과 심문에서 제시했다는 기록은 다릅니다.
- 복구 대사가 있다고 아직 승인되지 않은 비밀·추론·쟁점을 공개하지 않습니다.

## 5. 구현 위치

`GameService.reply`가 fixture·그래프 호출·서비스 수준의 복구를 담당합니다. `ReplyOutput.failure`도 기본 플레이 설정에서 승인 원문 fallback을 반환합니다.

서비스는 승인 계획 이후의 생성·검증 호출과 응답 검사를 감쌉니다. 모델 오류·검증 오류·내부 문맥 제한 오류 등은 설정이 허용하면 원문으로 복구합니다. 복구 응답도 `validate_generation`으로 식별자·필수 사실·원문 포함 여부를 확인합니다.

이후 `Engine.record_plan`과 `MongoRepository.commit`이 기존 원자적 저장 경로를 사용합니다. 모델 실패를 이유로 미검증 후보를 그냥 승인하는 방식은 아닙니다.

## 6. 여전히 오류가 될 수 있는 것

‘질문에 답한다’는 정책은 서버 접속 불가, 잘못된 인증·수사 토큰, 오래된 revision, 미획득 자료 주입, 잘못된 입력, 질문 한도, 종결 수사의 변경까지 무조건 HTTP 200으로 바꾸는 기능은 아닙니다. 생성 중 다른 행동이 먼저 확정됐다면 오래된 상태 위에 답변을 저장하지 않습니다.

현재 수사 전체 질문 한도 25회와 기존 게임 조건은 유지됩니다. 서버가 시작하지 못했거나 네트워크가 끊겼다면 대사 생성 API 자체에 도달할 수 없습니다.

## 7. 테스트 결과 읽기

플레이 테스트는 오류 주입 후에도 200·fallback·대화 저장이 되는지 확인합니다. strict 테스트는 false 설정으로 502·무소비·재시도를 확인합니다. 두 기대값은 서로 모순되지 않습니다.

실서버 LLM 검사 도구는 여전히 stop만 실제 모델 성공으로 인정합니다. 따라서 HTTP 200 fallback이면 사용자 대화는 제공됐지만 LLM 품질 검사는 실패일 수 있습니다.

## 8. 적용 순서

1. `.env`의 `CLICK_FALLBACK_ON_ERROR=true` 확인
2. FastAPI 재시작
3. Next.js 변경도 적용했다면 Next.js 재시작 및 브라우저 새로고침
4. 일반 질문·정보 없는 질문·자료 제시 질문 순서로 확인
5. API 응답의 finish_reason과 저장된 대화를 함께 확인
