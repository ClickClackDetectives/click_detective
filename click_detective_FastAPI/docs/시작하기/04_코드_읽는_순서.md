# 에이전트별 코드 구조와 읽는 순서

2026-11-16 기준. 코드를 위에서 아래로 따라가기 쉽도록 기본적인 `for`문, `if`문과 이름이 있는 중간 변수를 사용한다. 모든 Python 파일은 빈 줄·주석·docstring까지 포함하여 250줄 이내로 유지한다.

## 세 에이전트의 폴더

```text
app/dialogue/
├── preprocess_agent/              1. 질문과 승인 사실 준비
│   ├── agent.py                   PreprocessAgent: 전처리 실행
│   ├── planning.py                Planner: 말해도 되는 사실 선택
│   ├── approval_materials.py      제시한 자료와 새 쟁점 확인
│   ├── free_questions.py          자유 질문에 맞는 진술 선택
│   ├── retriever.py               승인 사실 안에서 관련성 검색
│   └── prompt.py                  생성 모델에 줄 자료와 지시 준비
├── inference_agent/               2. 후보 대사 만들기
│   └── agent.py                   InferenceAgent: 생성 모델 호출
├── validation_agent/              3. 후보 대사 검사
│   ├── agent.py                   ValidationAgent: 검사·재생성 결정
│   ├── output.py                  출력 형식 검사와 원문 복구
│   ├── verification.py            의미 보존 최종 확인
│   ├── verification_reports.py    검증 모델 호출과 보고서 재요청
│   ├── prompt.py                  검증용 자료와 지시 준비
│   ├── verification_prompting.py  배치와 재요청 지시 준비
│   ├── report_policy.py           공통 거절 조건
│   ├── evidence_checks.py         보고서 항목과 근거 번호 검사
│   ├── critical_facts.py          시각·수량 등 중요 의미 검사
│   ├── meaning_guards.py          행위자가 바뀐 오류 검사
│   ├── semantic_verification.py   검증 보고서와 후보 문장 형식
│   └── verification_units.py      승인 사실을 문장 단위로 구분
├── interrogation_graph.py         세 에이전트를 순서대로 연결
├── state.py                       에이전트가 함께 사용하는 작업 기록
├── schemas.py                     대화 요청·응답 형식
├── local_model.py                 공용 모델 실행과 GPU 잠금
├── model_loading.py               공용 모델 로딩
├── reply_validation.py            공통 응답 검사와 고정 대사 조립
└── diagnostics.py                 실행 기록
```

질문 승인 계획을 만드는 `Planner`는 그래프 실행 전에 호출되지만, 전처리와 같은 사실 준비 작업이므로 `preprocess_agent`에 둔다. 나머지 공용 모델과 데이터 형식은 세 에이전트가 함께 사용하므로 `dialogue` 바로 아래에 둔다.

사건 API와 수사 저장은 에이전트 자체의 작업이 아니다. 사건 조회 코드는 `app/cases`, 게임 진행·SQLite 저장·화면 정보는 `app/investigation`에서 확인한다.

## 실제 실행 순서

1. [수사 API](../../app/investigation/api/routes.py)의 `interrogate`가 질문을 받는다.
2. [수사 서비스](../../app/investigation/service.py)의 `GameService.change`가 요청을 예약한다.
3. [사실 선택](../../app/dialogue/preprocess_agent/planning.py)의 `Planner.prepare`가 이번에 말할 수 있는 사실을 고른다.
4. `GameService.dialogue_request`가 질문·인물·사실·최근 대화를 묶는다.
5. [그래프](../../app/dialogue/interrogation_graph.py)의 `InterrogationGraph.generate`가 세 단계를 실행한다.
6. [전처리](../../app/dialogue/preprocess_agent/agent.py)의 `PreprocessAgent.preprocess_agent`가 관련 사실과 프롬프트를 준비한다.
7. [생성](../../app/dialogue/inference_agent/agent.py)의 `InferenceAgent.inference_agent`가 모델에 후보 대사를 요청한다.
8. [검증](../../app/dialogue/validation_agent/agent.py)의 `ValidationAgent.validation_agent`가 형식과 의미를 확인한다.
9. 통과하면 [진술 기록](../../app/investigation/rules/testimony.py)을 반영하고 [저장소](../../app/investigation/persistence/repository.py)가 최종 상태를 저장한다.

검증에서 내용이 잘못되었다고 판단하면, 허용 횟수가 남아 있을 때 생성 단계로 돌아간다. 검증 보고서의 형식만 잘못되면 같은 후보 대사를 유지하고 보고서만 다시 요청한다.

`fixture` 모드는 AI 모델 대신 승인 원문을 연결한 고정 대사를 사용한다. `local` 모드에서는 생성과 의미 검증이 같은 모델을 목적별로 호출한다.

## 코드를 쉽게 읽기 위한 작성 방식

다음처럼 여러 작업을 한 표현에 넣는 코드는 일반 반복문으로 풀었다.

```python
selected_ids = []
for fact in selected_facts:
    selected_ids.append(fact.id)
```

조건에 따라 값이 바뀌는 부분도 분기해서 읽을 수 있게 했다.

```python
if settings.generation_output_format == "text":
    output_rule = "대사 원문만 출력하세요."
else:
    output_rule = "JSON으로 출력하세요."
```

위 두 코드는 작성 방식의 설명용 예시다. 실제 지시문 전문은 해당 소스에서 확인한다.

`catalog.py`에서는 파일 읽기 → 인물 목록 만들기 → 증거 목록 만들기 → 공개 응답 만들기 순서를 분리했다. 수사 화면과 대화 요청에서도 목록을 먼저 준비한 뒤 응답에 넣는다.

클래스·함수의 docstring은 첫 문장에서 역할을 설명하고, `Args`에 파라미터, `Returns`에 반환값을 설명한다. 단순한 연산에는 불필요한 설명을 반복하지 않고, 승인 사실 보존·미공개 자료 제외 같은 이유가 필요한 곳에 주석을 둔다.

## 코드 확인을 시작할 파일

세 에이전트가 궁금하면 `interrogation_graph.py`와 각 폴더의 `agent.py`부터 읽는다. API에서 저장까지 궁금하면 `investigation/service.py`의 `change`부터 읽는다. 사건 파일 읽기가 궁금하면 `cases/catalog.py`를 읽는다.

예전 위치에 남은 `agents.py`, `prompting.py`, `rag/retriever.py`, `investigation/planning.py` 등 짧은 파일은 기존 import를 연결하기 위한 파일이다. 실제 작업은 위 트리의 에이전트별 파일에서 확인한다. 각 에이전트 패키지의 `__init__.py`에서는 다른 에이전트를 자동으로 불러오지 않는다.

## 검사 명령

프로젝트의 가상환경을 활성화하고 `click_detective_FastAPI`에서 실행한다.

```bash
python -m pytest -q
python -m ruff check app scripts tests
python -m ruff format --check app scripts tests
```

파일 길이와 docstring 규칙도 테스트로 확인한다. 대상은 프로젝트에서 관리하는 `app`, `scripts`, `tests`의 Python 파일이며 가상환경과 외부 라이브러리는 제외한다.
